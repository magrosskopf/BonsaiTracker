# Stripe-backed care plan entitlement

The first paywalled care-plan feature includes Stripe integration rather than a placeholder-only paywall, because the feature is intended to validate paid product behavior end to end. The initial commercial model is a single monthly care-plan subscription, with no one-time purchases, tiers, or trial logic. Care-plan previews are visible before payment as a 12-month list of planned reminders; activation and system-reminder generation require entitlement. Users reach Stripe Checkout from the contextual care-plan paywall, then return to the bonsai/care-plan context rather than a separate pricing screen. Checkout return URLs are navigation only: care-plan activation is allowed only after the server-side entitlement reflects Stripe subscription state. Payment grants access but does not modify a bonsai; system reminders are created only when the user explicitly activates a care plan for that bonsai. The first UI scope is bonsai creation, bonsai detail, reminders, and profile; there is no standalone pricing page. The profile area links to Stripe Customer Portal for cancellation and payment-method management, while the app only displays the local care-plan access status. The application checks that internal entitlement for care-plan activation and reminder generation; Stripe is the payment source that creates or removes that entitlement, not the domain concept used throughout feature code. Stripe subscription statuses `active` and `trialing` grant the entitlement; `past_due`, `unpaid`, `canceled`, `incomplete`, `incomplete_expired`, and `paused` do not. When the entitlement ends, users cannot activate or resynchronize care plans, but already generated system reminders remain visible and actionable.
